# Modernization plan

What's left from the 2026-10-04 full-repo review after the fixes that shipped
in #274–#278. Each item is a staged migration, not a single change, for one
reason that runs through all of them:

**`index.html` is read as text.** `lab.html` fetches it (`lab.html:319`) and
lifts the fight model, the intel filters and every theme's colour variables out
of it by `// name:start … :end` markers and CSS rule shapes;
`scripts/build-fn-bundle.mjs` does the same to build send-reminders' bundle;
`check:lab`, `check:fightbot` and `check:bundle` hold all three to the app. Any
change to how `index.html` is shaped (minified, split, scripts moved out) has to
move those readers in the same step, or the Lab, FightBot and the Friday brief
silently stop matching the board.

The engine migration (`docs/MIGRATION.md`) is the template: one stage per PR,
a gate that proves nothing moved, never on a card day, a rollback per stage.

---

## 1. Split index.html into modules (and drop CSP `'unsafe-inline'`)

**Why.** ~9,700 lines of inline JS with ~540 top-level functions sharing global
state. The gates make it safe to change, but every change is a change to one
file, and the CSP must allow inline script, which removes most of its XSS value.

**Stages.**
1. **Lifted blocks first.** Move each `// name:start … :end` block the Lab and
   the bundle lift (fight model, intel filters) into its own file under
   `app/`, loaded with a plain `<script src>`. Point `loadKernel` and
   `build-fn-bundle.mjs` at the files instead of slicing HTML. Gate:
   `check:parity`, `check:lab`, `check:bundle` unchanged.
2. **Themes to `themes.css`.** Move the `:root` / `body[data-theme…]` rules
   out; `appThemeCss` reads the stylesheet instead of the page. Gate:
   `check:lab`'s per-theme colour comparison unchanged.
3. **Feature blocks.** Each `// x:start … :end` region (rooms, sports, safety,
   fighter-photos, what's-new, …) becomes a file, in dependency order, still
   classic scripts sharing globals. Every stage: `verify`, `SW_VERSION` bump,
   `scripts/lint-html.mjs` pointed at the new files.
   **Each extracted file is fetched the way `scoring.js` is, never cache-first.**
   `sw.js` serves other same-origin scripts cache-first, and an already
   controlled client gets the new page before the new worker activates, so a
   plain precache entry would run last release's module against this release's
   HTML. Request every extracted file with a version (`app/x.js?v=<SW_VERSION>`),
   add its path to `sw.js`'s network-first set alongside `scoring.js` and
   `lab/*.js`, and extend `check:lab`'s stale-copy test (which already proves an
   old `scoring.js` is refused) to cover them.
4. **Inline handlers.** Replace the ~230 `onclick="…"` attributes with
   delegated listeners (`data-action="…"`), a few dozen per PR. Gate: a
   `check:web` rule that counts inline handlers and only allows the number to
   fall.
5. **CSP.** Once no inline script or handler remains, remove `'unsafe-inline'`
   from `script-src`. Gate: `smoke` with a CSP-violation listener that fails on
   any report.
6. **Optional: ES modules + a bundler** (esbuild is already a dependency), once
   the globals have been narrowed to explicit imports.

## 2. Serve the minified build

**Why.** `npm run build` cuts `index.html` from 240 KB to 157 KB gzipped (−35%).

**Blocked by item 1.** Minifying strips the markers the Lab and the bundle
lift, and it would ship an artifact no gate has tested. After stage 1–2 of
item 1 nothing reads `index.html` as text any more; then:
1. Build `dist/` in `pages.yml` and run the browser gates (`smoke`, `check:tap`,
   `check:lab`, …) against `dist/` as well as the source.
2. Deploy `dist/`. Rollback: deploy the source again (one line in `pages.yml`).

## 3. `data.js` → `data.json`

**Why.** `data.js` is JavaScript generated by string templates and edited by
regex (`inject_results`), which is why `_shared/datajs.js`'s `parseDataJs`
exists and why a stray character can make it unparseable (#275 hardened the
injector). A wrapped App Store build also shouldn't execute downloaded code
(guideline 2.5.2).

**Stages.**
1. **Dual-write.** `scrape.py` builds a dict and writes it as `data.json`, then
   renders `data.js` from the same dict. Gate: a test that
   `parseDataJs(data.js)` deep-equals `data.json`. Cost: a second ~380 KB file
   committed every run, so do item 4 first or accept the churn for the
   migration's duration.
2. **Readers move one at a time**, each with its tests. The full list as of
   2026-10-04 (`git grep -l 'data\.js'`):
   - pipeline: `scrape.py`, `health.py`, `extra.py`, `intel.py`,
     `official_times.py`, `write_status.py`, `alert_calibration.py`, and
     `update.yml` (copies `data.js` as the health gate's baseline)
   - functions: `send-push` (`parseCards`), `kick-scraper`, `check-results`,
     `send-reminders` and `_shared/datajs.js`
   - readers: `lab.html`, `lab/engine.js`, `fightbot/core.mjs`,
     `scripts/build-fn-bundle.mjs`
   - build and checks: `build.mjs`, `validate-web.yml`, `check-web.mjs`,
     `scripts/lint-html.mjs`, `eslint.config.mjs`, and the tests that load it
   - last, the app itself (fetch instead of `<script src>`, keeping the
     purge-and-reload self-heal), `scoring.js`'s references and `sw.js`
3. **Results are dict edits.** `inject_results` updates the dict and
   re-renders, so no regex touches the file.
4. **Stop writing `data.js`**, only once a check that fails on any remaining
   `data.js` reference outside an explicit allow-list (the dual-write itself)
   has passed. The list above will have grown by then; the check, not the list,
   is what proves every consumer moved.

## 4. Move data commits off the app's history

**Why.** `update.yml` commits `data.js`, `odds-snapshots.jsonl` and friends
every ~5 minutes on fight nights, into the same history as the code. The log is
noisy and the repo only grows (`odds-snapshots.jsonl` is append-only, 2.6 MB
after 3.5 months).

**Constraints.** `kick-scraper` and `send-push` read the committed `data.js`
from `raw.githubusercontent.com/…/main` on purpose (see CLAUDE.md: "the gate
reads the COMMITTED data.js"), and Pages deploys from `main`.

**Stages.**
1. Rotate `odds-snapshots.jsonl` to monthly files once `odds_series.py` has
   frozen each card's open/close/CLV (it only needs the live window).
2. Commit data to a `data` branch; `pages.yml` assembles the site from `main`'s
   code plus the `data` branch's files; `DATA_URL` in `kick-scraper` and
   `send-push` points at the `data` branch. Each consumer moves with its own
   test.

## 5. Client error reporting

**Why.** 140 `catch {}` blocks keep the app up, but nothing tells anyone when
they fire. A deliberate trade-off, not a bug, but at App Store scale you need
to know.

**Decision needed.** Any reporting is new data collection: it needs a table
(or a vendor), a `privacy.html` update in the same change (CLAUDE.md rule), and
an entry in `delete_my_account()`. A minimal version: a `client_errors` table,
insert-only, rate-limited like `content_reports`, with no user content in the
payload.

## 6. Live polling at scale

Every open client polls Wikipedia every 2 minutes during a card. Fine for one
group of friends; at App Store scale move it server-side: the app already
receives results through `data.js` and pushes, so client polling can become a
fallback used only when `data.js` is stale.

## App Store: decisions, not code

These block a submission and none of them can be decided in code:

| Item | Guideline | Decision |
| ---- | --------- | -------- |
| "UFC" in the name, manifest and UI | 5.2.1 | Rebrand (the privacy page already says "Fight Cards") or get Zuffa's written permission |
| ESPN headshots, Wikipedia images | 5.2.2 | Licence them, or attribute Wikimedia images per their licence and drop ESPN |
| Wrapper approach | 4.2 | Capacitor or similar, with native features that justify an app (native push, widgets, Live Activities) |
| Push | — | Web Push doesn't run in an iOS app's web view: `send-push` needs an APNs path |
| CORS | — | Add the wrapper's origin (e.g. `capacitor://localhost`) to `ALLOWED_ORIGINS` in the Supabase function secrets; no code change |
| Unfiltered Grok roasts aimed at private people | 1.1 / 1.2 | Expect review scrutiny and a 17+ rating; consider a filtered mode for the store build |
| Odds and "Parlay Picks" | 5.3 | No real money, but expect 17+ and questions; keep it clearly a game |
| Support URL, contact email, privacy nutrition label, privacy manifest | 5.1 | A real contact address (not a GitHub issue) |
